Supabase · Policies

Supabase policies, explained simply

Your publishable key is not a secret — anyone can read it out of your page. So what stops a stranger from downloading every row in your database? Policies. A policy is one rule about who is allowed to see or change which rows.

5 things to know. That's the whole idea.
1
Point 1

A policy is a rule about rows

Think of a table as a spreadsheet of rows — one row per student, per club, per penguin. A policy is a rule attached to that table that answers one question: for this person, which rows are they allowed to see or change?

Without policies there are no rules at all, and "no rules" means "help yourself". This project is a live example. You don't need to log in, and you don't need a password — the publishable key from index.html is enough:

idle Nothing has been requested yet. 
// results will show up here
The students table is readable right now

Anyone who opens this page and presses that button gets real rows back — no login, no password. The demo deliberately shows only how many rows came back, not the contents, because those contents are real people's names. That is exactly what policies exist to prevent.

So a policy names three things:

  • Who — the role: strangers, logged-in users, or everyone.
  • What — reading, adding, changing, or deleting.
  • Which rows — the actual condition, like "only rows where the id is mine".
2
Point 2

Policies do nothing until you switch RLS on

Policies live inside a feature called RLS — Row Level Security. It's a switch on each table, and here's the trap: a table with RLS switched off ignores every policy you write. You can write ten perfect policies and a table with the switch off will still hand out everything. 

-- this is the switch. Nothing else matters until it's on.
alter table students enable row level security;

If you create a table in Supabase's Table Editor, the switch is turned on for you. If you create it by writing SQL, it is off by default and you have to turn it on yourself. That gap is where most accidental leaks come from.

How to check

In the dashboard, open Table Editor and look for the RLS badge next to the table name, or run select relname, relrowsecurity from pg_class where relname = 'students';. If it says false, the table is wide open to anyone holding your publishable key.

3
Point 3

Once RLS is on, the answer is no

This surprises everyone: turning RLS on doesn't protect the rows you care about and leave the rest — it locks everything. With RLS on and no policies written yet, nobody can read anything, not even you from your own web page. Policies are the exceptions you allow back in.

So the mental model is: RLS says no to everything, then each policy says yes to one specific thing. Want people to read but never delete? One read policy, no delete policy. Want everyone to see a public list but only edit their own row? Two policies.

A blocked read looks exactly like an empty table

If a read comes back as 200 OK with [], you genuinely cannot tell from the outside whether the table is empty or a policy just said no. In the panel above, locations returned nothing — and we have no way to know which of those two it was. It's a common source of confusion: the API is silent about refusal.

4
Point 4

The pattern you'll write over and over

Ninety percent of the policies you write will look like this one: you may only touch rows that belong to you. The magic ingredient is auth.uid() — it means "the id of the person who is logged in right now". If nobody is logged in, it's null, and null never equals anybody's id, so strangers get nothing. Automatically. 

-- READING: which existing rows can they see?
create policy "see your own student row"
on students
for select
to authenticated
using ( auth.uid() = user_id );   -- user_id is a column on the table

-- ADDING: what must a brand new row look like?
create policy "add your own student row"
on students
for insert
to authenticated
with check ( auth.uid() = user_id );

For this to work, the table needs a column holding the logged-in user's id — usually called user_id, and it has to be the same kind of id that auth.uid() returns. That one column is what ties a row to a person.

Keyword Means Used when
using Which existing rows they're allowed to touch Reading, changing, deleting
with check What a row is allowed to look like afterwards Adding, changing
to anon People who are not logged in Public pages, like a menu or a leaderboard
to authenticated People who are logged in Almost everything else
5
Point 5

Test it as a stranger, not as yourself

The classic mistake is testing while logged in as the owner of the database. Everything works, because the owner can do anything — and then a stranger opens your site and sees the lot. Test with the hat of the person you're worried about:

  • Open your page in a private window where you're logged out, and see what still appears.
  • Press the button above twice — logged out, then logged in. Right now both give the same answer, which is the problem; once your policies are written they should differ.
  • Look for a policy containing using ( true ) — that means "absolutely everyone", so make sure you meant it.
The secret key ignores every policy you write

The service_role key — the secret one — walks straight past RLS. That's why it can never go in an HTML page. It belongs only in an Edge Function or on your own server, where visitors can't read it.

The one-sentence version

Switch RLS on, assume it says no to everything, then write a policy for each thing you actually want to allow. If you can't name the rule that lets someone see a row, they shouldn't be seeing it.
