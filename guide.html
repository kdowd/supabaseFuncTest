Part 1

What a function actually is

Imagine you want to know how many clubs are in a database. You have two choices.

Option A: download the entire database into the browser and count them yourself. Slow, and now a stranger can read everything you downloaded.

Option B: send one short message that says "hey, count the clubs for me". Something on the server does the work and sends back just the answer.

Supabase functions are option B. The code sits on Supabase's side. Your HTML page is only allowed to ask. This matters because:

  • Your visitor never sees the logic, only the result.
  • The work happens next to the data, so it's fast.
  • You write it once and every page on your site can reuse it.
Part 2

The two kinds you'll meet

People say "Supabase function" for two different things. They are called from the same client, but they are not the same. This is the bit that confuses almost everyone at first, so learn the two names now:

Database function (“RPC”) Edge Function
What it is SQL saved inside your database A tiny program on a server
How you call it db.rpc('name') db.functions.invoke('name')
Good for Asking the database a question Talking to Stripe, OpenAI, sending email
Where it lives Written in the Supabase SQL editor A folder called supabase/functions/
The demo page uses the first kind

index.html calls db.rpc('get_clubs_bad', ...). So that function is SQL stored in the database — not a separate server. If you only remember one thing: rpc = database, functions.invoke = server.

Part 3

Reading the demo page line by line

Here is the whole of the working demo, with the boring parts removed:

<!-- 1. Load the Supabase library -->
<script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.117.3/dist/umd/supabase.js"></script>

<script>
  // 2. Which project are we talking to?
  let SUPABASE_URL = "https://decwucuwqnzrxzbxxifu.supabase.co";
  let SUPABASE_PUBLISHABLE_KEY = "sb_publishable_...";

  // 3. Make a client — your remote control
  const db = supabase.createClient(SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY);

  // 4. Ask the database to run a function
  async function getPenguins(rows) {
    let result = await db.rpc('get_clubs_bad', {
      row_limit: rows
    });

    // 5. The answer has two parts
    let data = result.data;
    let error = result.error;

    // 6. Stop if something went wrong
    if (error != null) {
      console.log("Oh dear");
      return;
    }

    if (data) {
      updateDisplay(data);
    }
  }

  // then do something with the rows
  function updateDisplay(data) {
    data.forEach((element, i) => {
      console.log(i, element);
    });
  }

  getPenguins(9);
</script>
1

The script tag loads the library

This pulls supabase-js off a CDN, so there is nothing to install and no build step. It must come before your own script, or supabase won't exist yet.

2

The URL and key say which project

The URL is your project's address. The publishable key is a guest pass — it identifies your project to the public and is designed to be visible in a browser. The secret key is the master key. It never goes in an HTML file.

3

createClient builds your remote control

db is the object you'll use for everything: db.rpc() for database functions, db.from() for tables, db.functions.invoke() for Edge Functions.

4

db.rpc() sends the request

rpc means "remote procedure call" — a fancy way of saying "run this function over there for me". The first argument is the function's exact name. The second is an object holding its inputs, so row_limit: 9 becomes the function's row_limit value.

5

The answer comes in two halves

Every call gives you back an object with data and error on it. The demo splits them onto their own lines — let data = result.data and let error = result.error — which is easier to read when you're starting out. Supabase never throws an exception at you; it always hands you both halves every single time.

The demo's function is async and uses await because it has to wait for the network. Without await you'd get a pending Promise instead of your rows.

6

Stop early if something went wrong

This is the safety check, and the demo gets it right. If error isn't null, something broke — return immediately, before anything else touches data. Only when error is null do you carry on to updateDisplay(data). (The demo logs "Oh dear" here, which is friendly but not much help when something really breaks — Part 6 comes back to that.)

You'll also see this written in shorthand

Supabase's own docs and most tutorials write the same two lines in one: const { data, error } = await db.rpc(...). That's called destructuring, and it means exactly the same thing as the demo's result.data and result.error. Use whichever you find easier to read — just know they're the same.

Part 4

The 4-step recipe

Any time you call a database function, it's these four lines of thinking:

1

Load the library

One script tag in your <head>.

2

Create the client

URL + publishable key. Do this once, at the top of your script.

3

Await the call

Grab data and error out of the result.

4

Check the error, then use the data

In that order. The demo does this correctly — it stops the moment something is wrong, and only reaches updateDisplay when nothing did. 

// the version the demo uses — one clear step at a time
let result = await db.rpc('function_name', {
  input_name: value       // whatever the function expects
});

let data = result.data;
let error = result.error;

if (error != null) {
  console.log(error.message);   // something broke — stop here
  return;
}

// data is now safe to use

// ---- the same thing in shorthand, which you'll see in the docs ----
const { data, error } = await db.rpc('function_name', {
  input_name: value
});

Part 6

5 mistakes everyone makes

1. Putting the secret key in your HTML

Anyone can open your page, press F12, and read your key. The secret key can delete every row you own. If a browser needs it, it's the wrong key — use the publishable key, and do privileged work inside an Edge Function.

2. An error message nobody can use

The demo's check is in the right place, but console.log("Oh dear") tells you nothing — not what broke, not which line. Log error.message (and error.code) instead, and on a real page show the visitor something they can act on. The other half of this mistake is skipping the check entirely: then data is null and the next line crashes.

3. Forgetting await

Without it you get a Promise, not your rows — so data is undefined and you crash with Cannot read properties of undefined. If a variable isn't what you expect, check the await first.

4. Thinking if (data) means "there are rows"

This is the demo's one real gap. An empty array is truthy in JavaScript, so if (data) is true even when the function returns []. The code runs, the loop runs zero times, and nothing appears. An empty result is a normal outcome, not an error — so check the length too: if (data && data.length > 0).

5. Typing the function name wrong

Names are exact and case-sensitive. If you misspell one you'll get PGRST202 — Could not find the function. That error is genuinely helpful: it usually even suggests the name you meant.

The fixed version

Same function, same easy-to-read style as the demo — it just checks for rows as well as errors, and says something useful when either goes wrong: 

async function loadClubs(limit) {
  showSpinner();

  let result = await db.rpc('get_clubs_bad', {
    row_limit: limit
  });

  let data = result.data;
  let error = result.error;

  hideSpinner();

  if (error != null) {
    showMessage('Something went wrong: ' + error.message);
    return;
  }

  // the check the demo is missing
  if (data == null || data.length === 0) {
    showMessage('No clubs to show yet.');
    return;
  }

  render(data);   // safe: we know it has rows
}
Built alongside index.html — the working demo in this folder. Open the browser console on that page to watch the function's reply come back.
