Supabase · Reading data

Ways to read data with JavaScript

One pattern, ten variations. Every call asks a table for rows and hands you back data and error — the only thing that changes is what you ask for. Every example below runs for real, so press the buttons and watch what comes back.

Start here

The shape of every call

This is the same call your getCountries.html page uses. Four pieces, and they always come in this order: 

const result = await db
    .from('countries')      // 1. which table
    .select('code, name')   // 2. which columns
    .order('name');         // 3. any instructions (this one sorts A-Z)

const data  = result.data;   // 4. the rows, or null if something broke
const error = result.error;  //    null if it worked, or what went wrong
PieceWhat it does
.from('countries')Picks the table. This is the only required part.
.select('code, name')Picks the columns. '*' means "all of them".
.order() .limit() .eq()Extra instructions. Chain as many as you like.
awaitWaits for the reply before carrying on. Without it you get a Promise, not rows.
Always check error before you use data

Supabase never throws an exception at you. When a call fails, data is null, so data.forEach(...) would crash. Check the error first, then use the rows.

The missing keyword

So where's the WHERE?

You may have noticed that the word WHERE never appears in any of this JavaScript. It is there all the same — the filters are the WHERE clause. Every .eq(), .ilike() or .gt() you chain on becomes one condition, and the client writes the SQL for you.

JavaScriptThe SQL it turns into
.eq('code', 'NZ')WHERE code = 'NZ'
.neq('code', 'NZ')WHERE code <> 'NZ'
.gt('id', 5)WHERE id > 5
.gte() .lt() .lte()>=   <   <=
.like('name', '%land%')WHERE name LIKE '%land%'
.ilike('name', '%land%')WHERE name ILIKE '%land%'  — ignores capitals
.in('code', ['NZ','AU'])WHERE code IN ('NZ','AU')
.is('country_code', null)WHERE country_code IS NULL
.not('course', 'eq', 'Fashion')WHERE NOT (course = 'Fashion')
.or('a.eq.1,b.eq.2')WHERE a = 1 OR b = 2
Chaining filters means AND

.ilike('campus','Wellington%').eq('course','Fashion') becomes WHERE campus ILIKE 'Wellington%' AND course = 'Fashion'. Every filter you add makes the list shorter, never longer — to widen it you need .or().

You can watch the WHERE go past

Open DevTools → Network, run any example, then click the request it made. The address ends in ?select=code%2Cname&code=eq.NZ — and that code=eq.NZ is the WHERE code = 'NZ', on its way to the database.

Why can't I just write my own SQL?

Because a browser must never be able to send whatever SQL it likes — that would be a serious hole. These filter methods are a small, safe vocabulary. Raw SQL from the browser is exactly what RPC is for, which you have already covered.

Putting it together

Chain them up

The instructions chain, and each one narrows things a bit more. Read it like a sentence: "from students, give me name and course, only where the campus starts with Wellington, sorted by name, first 5." 

const result = await db
    .from('students')
    .select('name, course')
    .ilike('campus', 'Wellington%')
    .order('name')
    .limit(5);
Order matters for .select() and filters, but not much else

Put .select() straight after .from() to keep things readable. Filters, sorting and limits can follow in any order — the result is the same.
